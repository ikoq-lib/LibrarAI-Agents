2026-07-11, 어린이자료실 5개 등록번호(EM19289, EM20608, EM23105, EM23122, EM23126)로 범위를 좁혀 B-06의 FN-01(배치 생성)→FN-02(스캔 대조)→FN-03(연속 미확인 판정) 흐름을 Supabase MCP로 실제 실행 검증했다.

**결과:** 1차 배치(TEST-2026-0601-어린이자료실, 06/01~06/05)에서 EM19289만 not_found, 나머지 4건 scanned, 가짜 바코드 EM99999999는 not_in_db로 정확히 분류됨. 2차 배치(TEST-2026-0710-어린이자료실, 07/10~07/20)에서도 EM19289가 다시 not_found → 2회 연속 미확인으로 결본(안) 판정 로직이 의도대로 동작함을 확인. 사용자 지시에 따라(테스트 목적, "사서 결본 최종 확정 가정") `books.material_status`를 EM19289에 대해 '소재불명'으로 실제 갱신함.

**Why:** 실제 서비스 투입 전 B-06 SQL 로직(scanned/not_found/not_in_db 분류, 연속 미확인 카운트)이 스키마와 맞물려 정확히 동작하는지 사서가 직접 확인하고자 함.

**중요 한계 발견:** DB에 대출·반납 이력을 시계열로 남기는 테이블이 없다(`books.loan_status`는 현재 스냅샷 값만 제공). 따라서 FN-03의 "재확인 대상 기간 내 대출·반납 이력 확인 시 자동 정상 복귀" 규칙은 현재 스키마로는 자동 검증이 불가능 — 향후 이 규칙을 실제로 자동화하려면 대출 이력 로그 테이블이 별도로 필요함. 실제 운영에서 이 규칙을 적용하려면 사서에게 수동 확인을 요청하거나, loan_history 테이블 도입을 B-01/DM-01 쪽에 제안해야 함.

**How to apply:** 향후 실제 정기 점검 배치를 돌릴 때도 동일한 INSERT 패턴(스캔 목록 VALUES → books LEFT JOIN → scanned/not_in_db, 그리고 대상 범위 reg_no 중 스캔 목록에 없는 것 → not_found)을 재사용할 수 있음. 다만 material_status 갱신은 실제 업무에서는 반드시 사서의 명시적 결본 확정 승인 후에만 실행해야 하며, 이번처럼 "가정하고 실행"하는 것은 검증 테스트 상황에 한정된 예외였음을 유의.

**Update 2026-07-11 (같은 날) — 테스트 데이터 원상복구 완료:** main 세션이 결과를 SQL로 직접 재확인한 뒤 (1) `EM19289.material_status`를 `'소재불명'` → `'이용가능'`으로 되돌리고, (2) `inspection_scans`에서 `batch_id like 'TEST-%'` 11건 삭제, (3) `inspection_batches`에서 `TEST-2026-0601-어린이자료실`/`TEST-2026-0710-어린이자료실` 2건 삭제했음. 최종 확인: `books` 총 73,390행 유지, EM19289 상태 정상 복구, 테스트 배치/스캔 잔존 0건, `disposal_candidates` 0행. **EM19289는 실제 소장 도서이므로, 향후 유사 검증 테스트를 할 때도 실제 데이터(real reg_no)를 건드린 뒤에는 반드시 원상복구를 확인할 것** — B-04-H/B-05 세션에서도 동일한 원칙(테스트 후 삭제/복구)이 적용됨.
