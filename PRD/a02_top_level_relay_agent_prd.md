# PRD — A-02 최상위이관 에이전트 (Top-Level Relay Agent)

**문서 버전:** 1.0  
**작성일:** 2026-05-23  
**소속 도메인:** D0 행정  
**에이전트 ID:** A-02  
**에이전트 유형:** Leaf Agent  
**참조 아키텍처:** 창녕도서관 사서 AI 에이전트 시스템 v3

---

## 1. 개요

### 1.1 목적

A-02 최상위이관 에이전트는 v3 아키텍처에서 **최상위 오케스트레이터로 기능이 이관된 통계보고서 생성** 역할의 명시적 연결 지점이다. 에이전트 자체가 독립적인 처리 로직을 수행하기보다, 전체 시스템에서 "통계보고서 기능이 어디서 왔는가"를 문서화하고 최상위 오케스트레이터와의 데이터 인터페이스를 정의하는 역할을 한다.

v3 이전 설계에서는 A-02가 도메인별 통계 취합 및 보고서 생성을 직접 담당했으나, v3에서 해당 기능이 최상위 오케스트레이터로 통합되었다. A-02는 이 이관의 인터페이스 레이어로서, 실적 데이터를 표준 형식으로 수집하여 최상위 오케스트레이터에 전달하는 **데이터 수집 브로커** 역할을 수행한다.

> **2026-07-07 변경(도메인 에이전트 계층 도입):** 최상위 오케스트레이터와 리프 에이전트 사이에 도메인 에이전트 계층(DM-01~DM-05, D1~D5 각 1개)이 신설되었다. D1~D5 리프 에이전트는 각자의 도메인 에이전트가 매월 실적을 취합해 A-02에 응답하므로, **A-02는 더 이상 D1~D5의 개별 리프(B01~F04, 총 27개)에 직접 요청하지 않는다.** D0 행정(A01·A03·A04, 공통도구 성격이라 도메인 에이전트 없음)만 예외적으로 지금처럼 개별 요청한다. 결과적으로 A-02의 수집 대상은 32개(리프 전체)에서 **8개(A01·A03·A04 + DM-01~DM-05)**로 축소된다. 이 변경으로 D3(구 D-05)·D4(구 E-05)가 담당하던 도메인 내 취합 역할은 폐지되고 DM-03·DM-04로 흡수되었다.

### 1.2 배경

최상위 오케스트레이터는 월간·상반기·연간 통계보고서를 생성한다. 도메인 에이전트 도입 이전에는 이를 위해 32개 리프 에이전트 각각의 실적 데이터가 필요했으나, 이제는 도메인 에이전트가 도메인 내부에서 1차 취합·표준화를 마친 뒤 A-02에 응답하므로 A-02가 상대해야 하는 소스 수가 크게 줄었다. A-02는 이 8개 소스(D0 3개 + 도메인 에이전트 5개)의 데이터를 표준 구조로 변환하여 최상위 오케스트레이터가 일관된 방식으로 수신할 수 있도록 한다.

### 1.3 범위

- **포함:** D0 3개 에이전트(A01·A03·A04) 및 5개 도메인 에이전트(DM-01~DM-05) 대상 실적 데이터 수집 요청 발송, 수신 데이터 표준화, 최상위 오케스트레이터 전달, 수집 실패 소스 탐지 및 사서 알림
- **제외:** 통계 계산 및 보고서 생성 (최상위 오케스트레이터 담당), 개별 에이전트 업무 처리, 도메인 내부 리프 실적 취합 (각 도메인 에이전트 담당), 예산 관리 (A-03 담당)

## 4. 기능 요구사항

### FN-01 정기 데이터 수집 (월간·반기·연간)

최상위 오케스트레이터의 보고서 생성 요청을 트리거로, A-02가 D0 3개 에이전트(A-01·A-03·A-04)와 5개 도메인 에이전트(DM-01~DM-05)에 실적 데이터 수집 요청을 발송한다(총 8개 소스 — 리프 에이전트에는 직접 요청하지 않음).

**수집 주기:**

| 보고서 유형 | 수집 시점 | 대상 기간 |
|------------|----------|----------|
| 월간 보고서 | 매월 초 | 전월 전체 |
| 상반기 보고서 | 6월 말 | 1~6월 (6월 잔여는 일평균 추정) |
| 연간 보고서 | 12월 말 | 1~12월 (12월 잔여는 일평균 추정) |

**추정 방식 (반기·연간 보고서):**
6월 또는 12월 1~2주차 일평균을 계산하여 잔여 기간에 적용한다.
예: 6월 1·2주차 일평균 100권 → 15~30일 = 100 × 16일 = 1,600권으로 추정

---

### FN-02 표준 데이터 수집 인터페이스

각 리프 에이전트는 A-02의 수집 요청에 응답하여 아래 표준 JSON 구조로 실적 데이터를 반환한다.

**수집 요청 구조:**
```json
{
  "request_type": "monthly_stats",
  "target_period": "2026-04",
  "requester": "A-02"
}
```

**응답 표준 구조 (도메인 에이전트 예시):**
```json
{
  "agent_id": "DM-01",
  "agent_name": "장서 도메인 에이전트",
  "period": "2026-04",
  "metrics": [
    {
      "metric_name": "신간 선정 건수",
      "value": 47,
      "unit": "권"
    },
    {
      "metric_name": "자료구입비 집행 금액",
      "value": 850000,
      "unit": "원"
    }
  ],
  "notes": "4월 D1 장서 도메인 실적 확정 완료",
  "status": "complete"
}
```

D0 소속(A-01·A-03·A-04)은 도메인 에이전트 없이 지금처럼 개별적으로 동일한 표준 구조로 응답한다.

**`status` 값:**
- `complete` — 정상 응답
- `partial` — 일부 데이터 누락 (notes에 사유 기재)
- `unavailable` — 해당 기간 업무 없음 (정상)
- `error` — 데이터 수집 실패

---

### FN-03 수집 실패 탐지 및 사서 알림

수집 요청 후 일정 시간 내 응답하지 않거나 `error` 상태로 응답한 소스(D0 3개 + 도메인 에이전트 5개)를 탐지하여 사서에게 알린다.

**알림 출력 예시:**
```
[A-02 데이터 수집 현황 — 2026년 4월]

수집 완료: 7개 소스
수집 실패: 1개 소스
 · DM-04 평생학습 — error (E-04 데이터 집계 중 SQLite 접근 오류)

※ DM-04 데이터는 사서가 수동으로 보완 후 최상위 오케스트레이터에 전달 필요합니다.
```

**Human-in-the-loop 필수:** 수집 실패 건은 사서가 해당 에이전트 담당자와 확인 후 수동 데이터를 A-02에 입력하며, A-02가 이를 표준화하여 최상위 오케스트레이터에 전달한다.

---

### FN-04 표준화 데이터 최상위 오케스트레이터 전달

수집 완료된 데이터를 도메인별로 구조화하여 최상위 오케스트레이터에 일괄 전달한다.

**전달 구조:**
```json
{
  "report_type": "monthly",
  "period": "2026-04",
  "collected_at": "2026-05-02T09:00:00",
  "collection_status": {
    "total_sources": 8,
    "complete": 7,
    "partial": 0,
    "unavailable": 0,
    "error": 1
  },
  "domains": {
    "D0": [...],
    "D1": [...],
    "D2": [...],
    "D3": [...],
    "D4": [...],
    "D5": [...]
  }
}
```

---

### FN-05 수동 데이터 보완 입력

사서가 수집 실패 에이전트의 데이터를 수동으로 A-02에 입력하면, A-02가 이를 표준 구조로 변환하여 저장 후 전달 패키지에 포함한다.

---

## 5. 데이터 흐름

```
[매월 초 / 반기 말 / 연말]
최상위 오케스트레이터 → A-02: 데이터 수집 요청
A-02 → D0(A-01·A-03·A-04) + 도메인 에이전트(DM-01~DM-05): 실적 데이터 요청 (일괄 발송, 총 8개 소스)
각 소스 → A-02: 표준 JSON 응답

A-02: 수집 실패 탐지
A-02 → 사서: 실패 에이전트 알림
사서 → A-02: 수동 데이터 입력 (실패 건 보완)

A-02: 전체 데이터 표준화·구조화
A-02 → 최상위 오케스트레이터: 완성 데이터 패키지 전달
최상위 오케스트레이터: 보고서 생성
```

## 7. Human-in-the-loop 정책

| 단계 | 사서 개입 여부 | 내용 |
|------|--------------|------|
| 정기 데이터 수집 발송 | 불필요 | 자동 실행 |
| 수집 실패 탐지 | 불필요 | 자동 탐지 후 사서 알림 |
| 수집 실패 건 보완 | **필수** | 사서가 데이터 직접 입력 |
| 최상위 오케스트레이터 전달 | 불필요 | 사서 승인 없이 자동 전달 |

## 8. 제약 및 예외 처리

| 상황 | 처리 방식 |
|------|----------|
| 리프 에이전트 응답 타임아웃 | 재요청 1회 후 `error` 처리, 사서 알림 |
| 데이터 형식 불일치 | 파싱 실패 항목 플래그 후 사서에게 수동 입력 요청 |
| 전체 수집 완료 전 오케스트레이터 요청 | 현재 수집 상태 반환, 완료 시 재전달 |
| 동일 기간 중복 수집 요청 | 기존 수집 데이터 반환 후 중복 방지 |

---

## 9. 비기능 요구사항

- 월간 수집은 매월 1일 오전 9시를 기준으로 자동 트리거된다.
- 8개 소스(D0 3개 + 도메인 에이전트 5개) 응답 대기 시간은 최대 10분으로 제한한다.
- 수집 이력은 연도 단위로 SQLite에 보존하며 삭제하지 않는다.
- 에이전트 응답 언어: 한국어

---

## 10. 향후 확장 고려사항

- 도메인 에이전트 수 변경 시 수집 대상 목록 자동 동기화 검토
- 수집 실패 패턴 분석을 통한 소스 안정성 모니터링 기능 추가 검토
- D0에도 향후 도메인 에이전트가 도입될 경우 FN-01 대상 목록 갱신 필요
