# PRD — F-04 소식지 에이전트 (Newsletter Agent)

**문서 버전:** 1.0
**작성일:** 2026-07-04
**소속 도메인:** D5 홍보협력
**에이전트 ID:** F-04
**에이전트 유형:** Leaf Agent
**참조 아키텍처:** 도서관 사서 AI 에이전트 시스템 v3

> **표기 안내:** 이 문서의 `FN-01`, `FN-02`... 는 에이전트 내부 기능(Function) 번호이며, 에이전트 ID인 F-01(SNS)·F-02(협력기관)·F-03(공모)와는 무관하다. F 도메인은 에이전트 ID 접두어와 기능 번호 접두어가 같아 혼동될 수 있어 `FN-` 접두어로 구분한다 (F-02·F-03 PRD에서 도입한 규칙과 동일).

---

## 1. 개요

### 1.1 목적

F-04 소식지 에이전트는 도서관 소식지(뉴스레터)를 정기적으로 제작하는 리프 에이전트다. D-01 동아리·D-02 행사기획·DM-03 독서문화 도메인·E-01 강좌기획·DM-04 평생학습 도메인 등 여러 에이전트로부터 지난 활동 하이라이트와 예정 프로그램 정보를 취합하여, 지역 주민·이용자·협력기관에게 배포할 소식지 hwpx 초안을 생성한다.

> **2026-07-07 변경:** 최상위 오케스트레이터 산하에 도메인 에이전트 계층(DM-01~DM-05)이 도입되면서, 하이라이트 데이터 취합 대상이 리프 신분의 D-05·E-05에서 이들을 흡수한 DM-03(독서문화)·DM-04(평생학습)로 변경되었다(D-05·E-05는 결번 처리).

### 1.2 배경

도서관 소식지는 개별 행사 단위 홍보(F-01 SNS·홍보물)와 달리, 일정 기간(월간 또는 계간) 동안의 여러 활동을 하나의 발행물로 모아 편집하는 매체다. 문제는 이 취합·편집 과정이 반복적이고, 여러 도메인(독서문화·평생학습)의 정보를 사서가 일일이 모아야 한다는 점이다. F-04는 이 과정을 자동화한다.

### 1.3 F-01 SNS 에이전트와의 구분

| 구분 | 목적 | 주기 | 콘텐츠 성격 |
|------|------|------|-----------|
| F-01 SNS | 개별 행사 단위 즉시 홍보 | 행사 발생 시마다 | 단일 행사 카드 + 캡션 |
| **F-04 (이 문서)** | 일정 기간 활동을 모은 정기 발행물 | 월간 또는 계간 (Config) | 다수 섹션 구성(하이라이트+예고+공지) |

두 에이전트는 같은 원천 데이터(D-01·D-02 등)를 참조할 수 있으나 산출물의 형태와 발행 주기가 다르므로 별도로 유지한다.

### 1.4 범위

- **포함:** 지난 활동 하이라이트 취합(DM-03·DM-04 연계), 예정 프로그램 안내 취합(D-01·D-02·E-01 연계), 소식지 섹션 편집 및 hwpx 초안 생성(A-01 호출), 발행 이력 관리, A-02 표준 데이터 제공
- **제외:** 소식지 실제 발행·배포(인쇄·홈페이지 게시·발송, 사서 직접 처리), 개별 행사 단위 홍보물(F-01 담당), 협력기관·의원 대상 개별 소통 문서(F-02 담당)

## 4. 기능 요구사항

### FN-01 발행 주기 및 섹션 구성 관리

발행 주기(월간/계간 중 Config로 선택)와 소식지 표준 섹션 구성을 관리한다.

**표준 섹션 구성 (기본값, Config로 조정 가능):**

| 섹션 | 내용 |
|------|------|
| 1. 인사말 | 도서관장 명의 짧은 인사 (사서가 직접 작성하거나 기본 문구 사용) |
| 2. 지난 활동 하이라이트 | 지난 기간 독서문화·평생학습 우수 활동 요약 |
| 3. 이달의 동아리 | 진행 중인 독서동아리 소식·모집 현황 |
| 4. 다가오는 프로그램 | 다음 기간 행사·강좌 예고 |
| 5. 도서관 안내 | 이용 시간, 휴관일 등 공지사항 (사서 입력) |

---

### FN-02 지난 활동 하이라이트 취합 (DM-03·DM-04 연계)

DM-03(독서문화 도메인)·DM-04(평생학습 도메인)로부터 지난 기간의 완료된 활동 데이터를 요청하여 하이라이트 후보를 구성한다.

**요청 구조 (F-04 → DM-03 / DM-04):**
```json
{
  "requester_agent": "F-04",
  "request_type": "highlight_summary",
  "target_period": "2026-06"
}
```

**응답 기대 항목 (DM-03):** 행사별 명칭·유형·참여 인원·모집충족률, 동아리 활동 요약
**응답 기대 항목 (DM-04):** 시즌 완료 프로그램별 명칭·수료율·주요 성과

**하이라이트 선정 기준:** 모집충족률 또는 수료율 상위 항목, 참여 인원이 많았던 활동, 사서가 별도로 지정한 항목을 우선 반영한다.

---

### FN-03 예정 프로그램 안내 취합 (D-01·D-02·E-01 연계)

D-01·D-02·E-01로부터 다가오는 활동 정보를 요청한다.

**D-01 동아리 응답 (기존 F-08 인터페이스 재사용):** 동아리명, 최근 회차 활동 요약, 선정 도서, 다음 회차 예정일·주제, 모집 중 여부

**D-02 행사기획 응답 기대 항목:** 다음 달 행사명·대상·기간·신청 방법 요약

**E-01 강좌기획 응답 기대 항목:** 차기 시즌 프로그램명·대상·모집 예정일

**소스 미응답 시:** 해당 섹션은 "다음 호에 안내 예정"으로 표기하고 사서에게 안내한다.

---

### FN-04 소식지 콘텐츠 편집 및 hwpx 초안 생성 (A-01 호출)

FN-02·FN-03에서 취합한 내용을 FN-01 섹션 구성에 맞춰 편집하고, A-01 공문서 에이전트를 호출하여 hwpx 초안을 생성한다.

**A-01 호출 입력 구성:** 발행 호수, 발행월, 섹션별 편집된 콘텐츠, 사서 작성 인사말·공지사항(있는 경우)

**문체 원칙:** 소식지는 공문서보다 친근한 어조를 사용하되, 사실 정보(날짜·장소·수치)는 정확하게 반영한다. 하이라이트 문구는 초안임을 명시한다.

> ⚠️ **Human-in-the-loop 필수:** 초안 생성 후 사서가 사실 오류·어조·분량을 검토·수정한 후 확정한다. 에이전트가 직접 발행하지 않는다.

---

### FN-05 발행 이력 관리

발행 완료된 소식지를 `newsletter_issues` 테이블에 기록한다.

**저장 항목:** `issue_id`, `period`(예: 2026-06 또는 2026-Q2), `title`, `sections_summary`, `hwpx_path`, `status`(`draft`/`published`), `published_date`

과거 호에서 다룬 하이라이트를 참고하여 동일 내용의 중복 게재를 피한다.

---

### FN-06 A-02 표준 데이터 제공

A-02 최상위이관 에이전트의 정기 데이터 수집 요청에 표준 구조로 응답한다.

```json
{
  "agent_id": "F-04",
  "agent_name": "소식지 에이전트",
  "period": "2026-06",
  "metrics": [
    { "metric_name": "발행 호수", "value": 1, "unit": "회" },
    { "metric_name": "수록 섹션 수", "value": 5, "unit": "개" }
  ],
  "notes": "2026년 6월호 발행 완료",
  "status": "complete"
}
```

## 8. 제약 및 예외 처리

| 상황 | 처리 방식 |
|------|----------|
| 특정 소스 에이전트 응답 없음 | 해당 섹션 "다음 호 안내 예정"으로 표기, 사서에게 안내 |
| 취합할 하이라이트가 전무한 기간 | 해당 섹션 생략 또는 "이번 호는 예정 프로그램 중심으로 구성됨" 안내 |
| 사서가 특정 섹션 생략 요청 | 요청대로 생략 후 섹션 구성 기록 |
| 동일 하이라이트가 이전 호와 중복 | 과거 발행 이력 확인 후 사서에게 중복 여부 안내 |
| 하이라이트 원본 수치와 실제 상황 불일치 의심 | 원본 데이터 그대로 표기하고 사서에게 재확인 요청 (임의 수정 금지) |

## 9. 비기능 요구사항

- 발행 주기(월간/계간)와 섹션 구성은 Config에서 조정 가능하다.
- 소식지 톤은 공문서보다 친근하되 수치·날짜 등 사실 정보는 원본 데이터를 그대로 반영한다.
- SQLite 데이터(발행 이력)는 연도 단위로 보존하며 삭제하지 않는다.
- 에이전트 응답 언어: 한국어
