## 1. 현재 구조와 이 설계가 바꾸는 것

### 1.1 현재 (2026-09-03 기준)

```
사용자 지시
  → chief 1차 턴 ──DISPATCH──→ DM ──ROUTE──→ 리프(병렬 ≤3)
                                  ↓ 리프 산출물 원문
                              DM 취합 → d.resultText
  → 집계 주입 → chief 2차 턴(표지·요약·예산·승인만, 4000토큰)
  → injectDomainDetail(스켈레톤, buildDomainDetailBody(run))
  → 채팅 메시지 1건으로 표시 → ⬇hwpx / ⬇PDF
```

핵심 성질: **최종 보고서는 통짜 생성물이 아니라 조립품이다.** 모델이 쓴 스켈레톤과, 코드가 이어붙인 도메인 상세 원문(`dispatches[i].resultText`)의 합이다(`LibrarAI.html:5566` `buildDomainDetailBody`, `:5569` `injectDomainDetail`).

**여기서 발견해 함께 고친 결함 2건**

1. **DM이 부분 수정 요청에 ROUTE 없이 인라인으로 답하면 상세가 쪼그라든다.** 실측 12,069자 → 3,046자. 보존해 둔 리프 원문(R-4)을 되물려 원문 수준을 유지시키는 폴백을 `runOneDispatch`에 추가했다. 재검증에서 3,046자 → 11,995자로 복구.
2. **chief가 REVISE 대신 보고서 전문을 직접 다시 써버린다.** 그 메시지는 `runId`가 없어 run과 끊기고, 화면 내용과 시스템 보관 내용이 어긋난다(설계 원칙 1 위반). REVISE 절에 "보고서 전문을 직접 다시 쓰지 말 것" 규칙을 넣어 차단했고, 재검증에서 안내문 36자 + REVISE 블록만 내는 것을 확인했다. **구조적 차단은 3단계 확정 게이트의 편집 잠금이 담당한다.**

**남은 관찰 사항(이번 범위 밖)**

- chief가 리프 id 대신 DM id를 target으로 고르는 경향이 있다. DM 단위 수정은 리프까지 재실행되므로 1~2콜이 아니라 4~5콜이 든다. 프롬프트에 "가능하면 리프 id" 규칙을 넣었으나 실측에서는 여전히 DM을 골랐다.
- DM 응답 앞에 `</think>` 문자열이 남는다(추론 모델 아티팩트). 이번 변경과 무관한 기존 현상.
- 진행 패널의 리프 요약이 `===ESCALATIONS===` 같은 첫 줄을 그대로 노출한다(`summarizeReply`). 기존 현상.

## 2. 데이터 모델

### 2.1 `chiefRuns[runId]` 확장

```js
{
  // ── 기존 ──
  status, scope, target_period, event_name, self_tasks, startedAt,
  dispatches: [{ agent, instruction, status, resultText, escalations, leafSteps }],

  // ── 신규 ──
  stage: "drafted" | "revising" | "confirmed" | "bundling" | "bundled",
  reportSkeleton: "",        // chief 2차 턴 원문(자리표시자 포함). 재조립의 좌변.
  reportTitle: "",           // 스켈레톤 첫 # 제목 캐시(파일명·zip 폴더명용)
  revisions: [               // 감사 로그. 확정본 신뢰의 근거.
    { at, kind: "edit"|"regen"|"add", target: "summary"|dispatchAgent|leafId, note }
  ],
  confirmed: {               // 확정 스냅샷. 번들의 유일한 입력.
    at, seq,                 // seq = 확정 차수(1차·2차…)
    reportText,              // 확정 시점 조립 결과 전문(동결)
    dispatches               // 확정 시점 깊은 복사
  } | null,
  bundle: {
    status: "idle"|"listing"|"generating"|"done"|"error",
    items: [ /* 6.1 문서 아이템 */ ],
    zipName
  } | null
}
```

### 2.2 `leafSteps` 확장 (R-4)

```js
leafSteps: [{ agentId, status, summary, text }]   // text = 리프 응답 원문
```

**용량 대책:** `chiefRuns`는 localStorage에 통째로 직렬화된다(`:5100`). 리프 원문까지 넣으면 run 1건이 수십~수백 KB가 된다. → **저장 시 최근 3개 run만 `leafSteps[].text`를 보존하고 그 이전 run은 저장 직전에 제거한다.** (`confirmed.dispatches`는 차수와 무관하게 유지 — 확정본은 증빙이다.)

### 2.3 표시본은 저장하지 않는다 (설계 원칙)

> **원칙 1 — 단일 진실 원천:** 화면에 보이는 보고서 전문은 **저장 대상이 아니라 파생값**이다.
> `renderReport(run) = injectDomainDetail(run.reportSkeleton, buildDomainDetailBody(run))`

수정은 **항상 조각**(`reportSkeleton` 또는 `dispatches[i].resultText`)에 반영하고, 표시본은 매번 다시 조립한다. 채팅 메시지의 `content`는 캐시로만 취급하고 재조립 시 갱신한다.

이유: "채팅 텍스트만 고치면 번들이 옛 데이터로 생성되는" 사고를 구조적으로 차단한다. 조각을 거치지 않은 수정은 존재할 수 없게 만든다.

### 2.4 메시지 ↔ run 연결 (R-1)

```js
// 변경 전 (:5698)
const stream2 = makeStreamHandler(setChiefMsgs);
// 변경 후 — makeStreamHandler는 이미 extra를 지원한다
const stream2 = makeStreamHandler(setChiefMsgs, { runId, kind: "report" });
```

`renderChiefAssistant`(`:6176`)에서 `msg.kind === "report"`이면 `ReportDocument`에 `run={chiefRuns[msg.runId]}`를 함께 넘긴다.

## 3. 파트 A — 부분 수정 경로

### 3.1 섹션 분해

조립 결과를 5개 편집 단위로 나눈다. 경계는 이미 프롬프트가 강제하는 구조(`:3200`~`:3211`)를 그대로 쓴다.

| 단위 | 소유 조각 | 편집 | 재생성 |
|---|---|---|---|
| 표지·총괄 요약 | `reportSkeleton` | O | chief 2차 턴 재호출 |
| 도메인별 상세 (DM 단위) | `dispatches[i].resultText` | O | 해당 DM+리프 재실행 |
| 리프 산출물 (리프 단위) | `dispatches[i].leafSteps[j].text` | O | 해당 리프 1건만 재호출 |
| 기획담당 직접 수행 업무 | `reportSkeleton` | O | chief 2차 턴 재호출 |
| 예산 개요 / 승인 필요 항목 | `reportSkeleton` | O | chief 2차 턴 재호출 |

> 리프 단위 재생성 후에는 해당 DM의 `resultText`를 다시 만들어야 한다. **DM 재취합 호출 없이**, 코드가 `resultText` 안에서 그 리프 섹션(`### B-02 희망도서` 헤딩 블록)을 새 원문으로 치환한다. DM은 리프 산출물을 원문 그대로 포함하도록 지시되어 있으므로(`:5653`) 헤딩 기준 치환이 성립한다. 치환 실패(헤딩 불일치) 시에만 DM 재취합 1콜로 폴백한다.

### 3.2 세 가지 수정 유형

#### 유형 1 — 직접 편집 (0 콜)

- 섹션 헤더 우측 `✏️` → 해당 조각을 textarea로 열고 저장.
- 저장 시: 조각 갱신 → `revisions`에 `{kind:"edit"}` 기록 → 재조립 → 메시지 content 갱신.
- 오탈자·날짜 표기·금액 표기·문장 삭제가 여기 해당한다. 실무 수정의 대부분이 이 경로여야 한다.

#### 유형 2 — 부분 재생성 (1~2 콜)

- 섹션 헤더 우측 `🔄` → 지시문 입력("행사 예산 200만원으로 축소") → 실행.
- 대상이 DM이면 `runOneDispatch`를 **그 dispatch 하나만** 재호출한다. 기존 함수를 그대로 재사용하되 `d.instruction`에 수정 지시를 덧붙인다:

```
{원래 instruction}

[수정 요청 — 최고관리자] {지시문}
직전 산출물을 전면 재작성하지 말고 이 수정만 반영해 같은 구조로 회신하십시오.
```

- 대상이 리프면 `runChiefLeafChain`의 `runLeaf` 1건만 호출한다.
- 완료 후 **요약 갱신 여부를 묻는다**(수치가 바뀌면 총괄 요약·예산 개요가 어긋나므로). 기본값 "갱신함".

#### 유형 3 — 도메인 추가 (2~3 콜)

- 보고서 하단 `➕ 도메인 추가` → DM 선택 + 지시문 → `run.dispatches`에 append 후 그 1건만 실행 → 요약 갱신.

### 3.3 요약 갱신 전용 호출

DISPATCH를 다시 내지 못하게 막은 전용 접미사로 chief 2차 턴만 재호출한다.

```
CHIEF_REVISE_SUFFIX 내용:
## 부분 수정 모드 — 추가 규칙
- 이 요청은 이미 작성된 통합 문서의 일부만 갱신하는 것입니다. 새 DISPATCH를 절대 내지 마십시오.
- 표지·총괄 요약·기획담당 직접 수행 업무·예산 개요·승인 필요 항목 절만 다시 작성합니다.
- 도메인별 상세 자리에는 반드시 자리표시자 한 줄만 두십시오(시스템이 최신 원문으로 채웁니다).
- 변경되지 않은 도메인의 요약 문장은 그대로 유지하고, 변경된 도메인 문장만 고칩니다.
```

주입 메시지:

```
[부분 수정 — 시스템 자동 주입]
변경된 대상: DM-03 독서문화
변경 사유: {지시문}
변경 후 해당 도메인 산출물 발췌(4000자):
{새 resultText 앞부분}

위 변경만 반영해 요약·예산·승인 절을 갱신하십시오.
```

`max_tokens: CHIEF_COMPILE_MAX_TOKENS`(4000) 그대로. 반환값이 새 `reportSkeleton`이 된다.

### 3.4 채팅으로 들어온 수정 요청 라우팅 (R-2 해결)

chief 시스템 프롬프트에 규칙과 블록을 추가한다.

```
## 직전 계획서 수정 요청
직전에 작성한 통합 문서가 있고 최고관리자가 그 문서의 일부 수정을 요청하면
(예: "행사 예산 줄여줘", "장서 쪽만 다시", "요약 문구 고쳐"),
DISPATCH를 내지 말고 아래 블록만 출력하십시오. 전체 재실행은 금지입니다.

===REVISE===
{"target": "dm03-reading-culture-domain", "instruction": "9월 행사 예산 200만원으로 축소", "refresh_summary": true}
===REVISE_END===

- target: DM id · 리프 id · "summary"(요약·예산·승인 절만) 중 하나
- 대상 기간 자체가 바뀌거나("10월로 바꿔") 도메인 구성을 새로 짜야 하면 REVISE 대신 DISPATCH를 냅니다.
```

`sendChiefMessage` 흐름 변경:

```js
const firstReply = await requestApi(...);
const revise = parseReviseBlock(firstReply);          // ← 신규, DISPATCH보다 먼저 확인
if (revise) { await applyRevision(latestRunId, revise, signal); return; }
const dispatchMeta = parseDispatchBlock(firstReply);
if (!dispatchMeta) { stream.finalize(guardPlaceholder(firstReply)); return; }  // ← R-3 방어
```

`guardPlaceholder()`: 응답에 `===보고서시작===`이 있는데 run 컨텍스트가 없으면 자리표시자 줄을 제거하고 "부분 수정은 보고서 패널의 ✏️/🔄 버튼을 사용해 주세요" 안내를 덧붙인다. 자리표시자 문자열이 사용자 화면에 노출되는 일을 원천 차단한다.

### 3.5 확정 이후의 수정

`stage === "confirmed"`인 run에 수정이 들어오면 즉시 적용하지 않고 확인한다.

> "1차 확정본이 이미 있어요. 수정하면 2차 확정본이 되고, 1차로 만든 문서 번들과는 내용이 달라져요. 진행할까요?"

승인 시 `confirmed.seq + 1`로 새 차수를 열고 이전 확정 스냅샷은 그대로 남긴다.

## 4. 파트 B — 확정 게이트

- `ReportDocument` 헤더에 `✅ 확정` 버튼 추가(`⬇hwpx` / `⬇PDF` 좌측).
- 클릭 시 확인 모달: 대상 기간, 도메인 수, 수정 이력 건수, "확정하면 이 내용으로 실행 문서를 생성합니다".
- 확정 처리:

```js
run.confirmed = {
  at: new Date().toISOString(),
  seq: (prevSeq || 0) + 1,
  reportText: renderReport(run),
  dispatches: JSON.parse(JSON.stringify(run.dispatches)),
};
run.stage = "confirmed";
```

- 확정 후 보고서 패널 상단에 `✅ 1차 확정 · 2026. 9. 3. 14:20` 배지. 편집 버튼은 비활성 + `🔓 수정하기`(→ 3.5 분기)로 대체.
- 확정과 동시에 `📦 실행 문서 생성` 버튼이 나타난다.

### 4.1 구현 현황 (2026. 9. 3.)

3단계 완료. `LibrarAI.html`에 반영된 내용:

| 항목 | 구현 |
|---|---|
| 데이터 모델 | `run.stage`("drafted"/"confirmed") + `run.confirmed`{at, seq, reportText, dispatches} |
| 확정 | `confirmChiefRun(runId)` — `renderReport(run)` 결과와 `dispatches` 깊은 복사를 동결 |
| 확정 해제 | `reopenChiefRun(runId)` — 이전 스냅샷은 증빙으로 남기고 편집 잠금만 해제 |
| UI | 보고서 헤더에 `✅ 확정` → 확인 스트립(대상 기간·도메인 수·수정 이력·직전 차수) → 확정 시 `✅ N차 확정 · 2026. 9. 3. 13:39` 배지 + `🔓 수정하기` |

## 5. 파트 C — 문서 매니페스트

### 5.1 파일과 로딩

새 파일 `doc_manifest_data.js`를 `annual_schedule_data.js`와 같은 방식으로 script 태그 로드한다(`LibrarAI.html:11` 옆). 전역 상수 2개를 노출한다.

- `DOC_MANIFEST_ROWS` — 업무별 문서 세트
- `DOC_SKELETONS` — 문서 종류별 텍스트 골격(옵션 A의 핵심, 8장)

### 5.2 스키마

```js
{
  taskName: "희망도서수서",          // annual_schedule_data.js의 taskName과 정확히 일치
  owner:    "dm01-collection-domain",
  leaf:     "b02-wishlist",          // 문서 생성 호출 대상. null이면 chief 직접
  repeat:   "monthly",               // monthly | weekly | quarterly:[2,5,8,11] | yearly:[1] | conditional | manual
  condition: null,                   // "강사 있음" 등. 코드 키워드 판정 + 사서 체크박스
  docs: [
    { tpl:"TPL-014", kind:"기안문", format:"hwpx", skeleton:"SK-구입건의",
      title:"{m}월 희망도서 구입 건의" },
    { tpl:"ATT-007", kind:"붙임",   format:"xlsx", skeleton:null,
      title:"{m}월 희망도서 구입 목록" }
  ]
}
```

- `tpl: null` → 등록 양식 없음. `TPL-001` 기본형 + 생성 목록에 `⚠ 양식 미등록` 배지.
- `format: "none"` → 문서 산출물이 아님(홍보 문구·SNS 등). 매니페스트에는 남기되 번들에서 제외.
- `repeat: "manual"` → 건수를 코드가 계산할 수 없다. 생성 목록에서 사서가 수량을 입력한다(기본 0).
- `title`의 `{n}`은 차수(주차·분기), `{m}`은 월.

**`leaf`는 반드시 앱의 실제 라우팅 id를 쓴다.** `.claude/agents/`의 파일명이 아니라 `LibrarAI.html`의 `DOMAINS[].agents[].id`이며, D·E 도메인은 옛 탭 id를 그대로 쓴다. 5.5 표의 "담당" 열(B-01·D-02 등)과의 매핑은 다음과 같다.

### 5.3 수량 계산 규칙

| repeat | 계산 |
|---|---|
| `monthly` | 1건 |
| `weekly` | 대상 월의 주 수(그 달 첫 월요일 기준, 4 또는 5) |
| `quarterly:[2,5,8,11]` | 대상 월이 배열에 있으면 1건, 없으면 0건 |
| `yearly:[1]` | 대상 월이 배열에 있으면 1건 |
| `conditional` | 조건 판정 통과 시 1건 |
| `manual` | 코드가 계산하지 않는다. 생성 목록에서 사서가 수량 입력(기본 0) |

주간 계획(`scope: "weekly"`)에서는 `weekly`가 1건, `monthly`는 그 주에 해당 일자가 포함될 때만 1건.

### 6.2 생성 호출

**문서 1건 = 콜 1회.** 담당은 매니페스트의 `leaf`(없으면 chief 프롬프트). A-01을 경유하지 않는다 — A-01은 `template_id` JSON 인터페이스라 웹앱 리프 호출 경로와 형태가 다르고, 리프가 도메인 지식을 이미 갖고 있다. 대신 A-01이 보유한 **양식 규격(결재선·종결어·공개구분)을 프롬프트로 주입**한다.

```js
const buildHwpxBlob = async (bodyText) => { /* 기존 :3698~3701 */ };

```

### 7.3 압축 설정

hwpx·xlsx는 그 자체가 zip이다. 이중 압축은 시간만 쓰고 크기는 거의 안 준다.

```js
zip.file(path, blob, { compression: "STORE" });   // 문서 파일
zip.file("_생성목록.md", md);                      // 텍스트는 기본 DEFLATE
await zip.generateAsync({ type: "blob" });
```

### 7.4 파일명 규칙

- `{순번2자리}_{문서명}({기안문|붙임}).{ext}`
- 금지문자 `\ / : * ? " < > |` 제거, 공백은 `_`, 40자 절단 — 기존 `hwpxFilenameFrom`(`:3712`) 규칙을 함수로 추출해 공용화.
- 중복 시 `_2` 접미사.

문서 목록을 그대로 진행 패널로 전환한다(디스패치 진행 패널과 같은 시각 언어).

```
  [완료] 제36차 희망도서 구입 건의          B-02
  [진행] 제36차 희망도서 구입 목록          B-02
```

### 8.1.1 소식지 골격 2종 (TPL-031 · ATT-015)

- **항목기호를 쓰지 않는다.** `1.` `2.` 없이 서술 1문단으로 시작한다(실물 샘플 확인).
- `{통권}`은 **창간호부터 누적된 전체 권호**이며 월 1회 발행마다 +1이다. 코드가 계산한다 — 기준점 **2026년 9월 = 제138호**에서 대상 월과의 개월 차를 더한다.

```js
// 통권 = 138 + (대상월 - 2026-09) 개월
const ISSUE_BASE = { year: 2026, month: 9, no: 138 };
const issueNo = (y, m) => ISSUE_BASE.no + (y - ISSUE_BASE.year) * 12 + (m - ISSUE_BASE.month);
// 2026-10 → 139, 2026-12 → 141, 2027-01 → 142
```

  결호·합본이 생겨 실제 호수가 어긋나면 기준점(`ISSUE_BASE`)을 갱신한다.

## 10. 구현 순서

각 단계는 독립적으로 검증 가능하며, 앞 단계가 끝나면 그 상태로 멈춰도 회귀가 없다.

| 단계 | 내용 | 검증 |
|---|---|---|
| **1** | 데이터 모델 확장, `runId` 연결(R-1), `leafSteps.text` 보존(R-4), `renderReport()` 파생값화, localStorage 트리밍 | 기존 월간 계획 흐름이 동일하게 동작. 새로고침 후 보고서 재조립 성공 |
| **2** | 부분 수정 — ✏️ 직접 편집 → 🔄 부분 재생성 → `===REVISE===` 라우팅(R-2) → `guardPlaceholder`(R-3) | "예산 줄여줘"에 5개 도메인 재실행이 일어나지 않음. 자리표시자 미노출 |
| **3** | 확정 게이트 — 스냅샷·차수·잠금·배지 | 확정 후 편집 시 차수 승격 확인 모달 |
| **4** | `doc_manifest_data.js` + 생성 목록 체크리스트 (생성 없이 목록만) | 9월 확정본에서 14건 목록 표시 · 양식 미등록 배지 정확 · 독서동아리 수량 입력칸 노출 |
| **5** | 문서화 패스 + 번들러 — `extractDocBlocks`(R-6), blob 분리, zip, 진행 UI | zip 1개에 hwpx 12·xlsx 7·`_생성목록.md` 포함, 실패 1건 있어도 나머지 완주 |

1~3단계는 문서 번들과 무관하게 그 자체로 쓸모가 있다(수정 때마다 전체 재실행하던 문제 해결). 4~5단계가 본 기능이다.
