# PRD — DM-04 평생학습 도메인 에이전트 (Lifelong Learning Domain Agent)

**문서 버전:** 1.0
**작성일:** 2026-07-07
**소속 도메인:** D4 평생학습 (총괄)
**에이전트 ID:** DM-04
**에이전트 유형:** 도메인 에이전트 (최상위 오케스트레이터와 D4 리프 에이전트 사이의 중간 관리 계층)
**참조 아키텍처:** 도서관 사서 AI 에이전트 시스템 v3

---

> **표기 안내:** 이 문서의 `FN-01`, `FN-02`... 는 DM-04 내부 기능 번호다. `E-01`~`E-04`는 D4 평생학습 도메인의 리프 에이전트, `chief-coordinator`는 최상위 오케스트레이터를 가리키는 실제 에이전트 참조다.
>
> **E-05 폐지 통합:** 본 PRD의 FN-02~FN-06은 폐지된 `PRD/e05_result_report_agent_prd.md`(E-05 결과보고 에이전트)의 기능을 그대로 흡수·이관한 것이다. 세부 로직(검증 기준, 보고서 표 구성, 종합 점수 계산식 등)은 E-05 PRD와 동일하며, 여기에 FN-01(상위 지시 분배)이 신규로 추가되었다.

---

## 1. 개요

### 1.1 목적

DM-04 평생학습 도메인 에이전트는 D4 평생학습 도메인(E-01 강좌기획 → E-02 강사공모 → E-03 모집 → E-04 운영일지의 시즌 단위 선형 파이프라인)을 총괄하는 중간 관리 계층이다. 최상위 오케스트레이터로부터 정책·기획 지시를 받아 해당 리프에 분배하고, 시즌 종료 시 E-04로부터 운영 실적을 수신해 통합 결과보고서를 생성한 뒤 A-02의 표준 데이터 수집 요청에 응답한다.

### 1.2 배경

기존에는 E-05 결과보고 에이전트가 파이프라인의 마지막 단계로서 E-04 실적을 취합해 보고서를 생성하고 E-01에 피드백하는 역할을 리프 신분으로 수행했다. 도메인 에이전트 계층 도입에 따라 이 역할이 DM-04로 흡수되었다(E-05는 결번 처리).

### 1.3 리프-투-리프 직접 협업과의 관계 (중요)

**DM-04는 E-01→E-02→E-03→E-04로 이어지는 기존 파이프라인 인계에 개입하지 않는다.** E-02가 E-03에 확정 강사 정보를 넘기거나, E-03이 E-04에 수강생 명단을 인계하는 것은 지금처럼 리프끼리 직접 처리한다. DM-04가 관여하는 것은 오직 다음 두 가지뿐이다:
- **하향(top-down):** 최상위의 정책/기획 지시를 받아 어느 리프가 처리할지 배분
- **상향(bottom-up):** 시즌 종료 시점의 실적 취합과 보고서 생성, 그리고 E-01 피드백

### 1.4 범위

- **포함:** 최상위 지시 수신·분배(FN-01), 계획서 초안 생성·전달(FN-02), E-04 시즌 운영 실적 데이터 수신·검증(FN-03), A-03 예산 집행 현황 조회(FN-04), 시즌 결과보고서 hwpx 초안 생성(FN-05), E-01 수강 실적 피드백(FN-06), A-02 표준 데이터 수집 응답(FN-07), 연간 누계 보고(FN-08)
- **제외:** 각 리프 에이전트의 개별 운영 업무(E-01~E-04 담당), 파이프라인 내 리프 간 직접 인계의 중계, 결과보고서 실제 제출·결재(사서 직접 처리), 예산 집행 결정(A-03 담당)

## 3. 기능 요구사항

### FN-01 최상위 지시 수신 및 분배

chief-coordinator로부터 D4 평생학습 관련 정책·기획 지시를 수신하여 해당 리프에 전달한다. 대부분의 지시는 시즌 초 기획 단계(E-01)에 영향을 미치지만, 진행 중인 시즌에 관한 지시는 관련 단계(E-02~E-04)로 직접 전달한다.

**처리 절차:** 1) 지시 분석 후 대상 리프 식별 2) 모호하면 chief-coordinator에 확인 질문 3) 전달 완료 후 결과를 상위 보고

> ⚠️ 파이프라인 내 리프 간 인계(E-01→E-02→E-03→E-04)에는 관여하지 않는다.

---

### FN-02 계획서 초안 생성 및 최상위 전달

chief-coordinator의 월간·특별 계획 조회 요청에 응답한다. **DM-04가 직접 새 계획을 만들어내는 것이 아니라, E-01이 이미 보유·확정한 시즌 기획 정보를 취합해 도메인 수준 요약으로 편집한다.** D4는 시즌 단위(상반기/하반기 등 수개월) 파이프라인이라 D3처럼 매월 새 계획이 있는 것은 아니다 — 시즌 기획이 진행 중이거나 막 확정된 달에만 유의미한 응답이 나온다.

**요청 (chief-coordinator → DM-04):**
```json
{ "requester_agent": "chief-coordinator", "request_type": "plan_request", "scope": "monthly", "target_period": "2026-08" }
```

**처리 절차:**
1. E-01에 해당 시점의 시즌 기획 진행 상태를 조회한다 — 사전 질의·후보 추천 단계(미확정)면 "진행 중"으로, 세부계획서 사서 확정 완료 상태면 확정 내용을 요약한다.
2. 진행 중인 시즌이 이미 운영 단계(E-02~E-04)에 있고 신규 기획 활동이 없으면 "해당 없음"으로 응답한다.
3. E-01 응답을 그대로 편집·요약한다. 사서 확정 전 후보 단계 정보는 "미확정 후보"임을 반드시 명시한다.

**응답 (DM-04 → chief-coordinator):**
```json
{
  "agent_id": "DM-04",
  "agent_name": "평생학습 도메인 에이전트",
  "scope": "monthly",
  "period": "2026-08",
  "has_plan": true,
  "plan_summary": "2026년 하반기 세부계획서 사서 확정 완료(캘리그라피·북아트 2개 프로그램). 8월 중 강사공모(E-02) 착수 예정.",
  "source_leaf": ["E-01"],
  "status": "complete"
}
```

시즌이 이미 운영 중이라 신규 기획 활동이 없는 달은 `"has_plan": false, "status": "unavailable"`로 응답한다 — 오류가 아니다.

> DM-04는 이 계획 초안에 대해 hwpx 문서를 직접 생성하지 않는다 — chief-coordinator가 5개 도메인 응답을 통합 계획서 한 편으로 편집할 때 A-01을 호출한다.

---

### FN-03 E-04 운영 실적 데이터 수신 및 검증

시즌 종료 시 E-04로부터 운영 실적 데이터를 수신하고 필수 항목을 검증한다. (E-05 PRD FN-01과 동일)

**필수 검증 항목:** 총 진행 회차 수(>0), 수강생별 출석률(0~100%), 수료 인원(≤등록 인원), 강사비 집행 회차 수(≤진행 회차 수)

**검증 실패 시:** 누락·오류 항목을 목록화하여 사서에게 E-04 재확인 요청.

---

### FN-04 예산 집행 현황 조회 (A-03 호출)

A-03에서 해당 시즌 강사비·운영물품비 집행 현황(편성액·집행액·잔액·집행률, 도메인간 유용 발생 건수·금액)을 조회한다.

---

### FN-05 시즌 결과보고서 초안 생성 (A-01 호출)

E-04 실적과 A-03 예산 데이터를 통합해 결과보고서 hwpx 초안을 생성한다. 복수 프로그램은 하나의 보고서로 통합한다. (E-05 PRD FN-03과 동일 구성)

**결과보고서 구성:** ①운영 개요 ②운영 실적(표, 프로그램별 정원·접수·수료·출석률·진행 회차) ③수강생 현황 ④예산 집행 현황 ⑤성과 및 개선사항

**자동 생성 기준(Config 조정 가능):** 수료율 85%↑/70%↓, 모집충족률 100%↑, 휴강 2회↑, 중도 포기 3인↑ 등 — 상세 문구 템플릿은 E-05 PRD FN-03을 그대로 따른다.

> ⚠️ **Human-in-the-loop 필수:** 초안 생성 후 사서 검토·수정·결재 후 사용.

---

### FN-06 E-01 수강 실적 데이터 피드백

결과보고서 사서 확정 후 E-01의 `course_history` 테이블에 수강 실적 데이터를 전달한다(E-05 PRD FN-04와 동일 형식·종합 점수 계산식: 모집충족률×0.4 + 출석률×0.4 + 수료율×0.2). 확정 직후 자동 전달.

---

### FN-07 A-02 표준 데이터 수집 응답

```json
{
  "agent_id": "DM-04",
  "agent_name": "평생학습 도메인 에이전트",
  "period": "2026-상반기",
  "metrics": [
    { "metric_name": "총 프로그램 수", "value": 2, "unit": "개" },
    { "metric_name": "총 수강생 수", "value": 26, "unit": "명" },
    { "metric_name": "평균 수료율", "value": 88.5, "unit": "%" },
    { "metric_name": "강사비 집행액", "value": 1500000, "unit": "원" }
  ],
  "notes": "상반기 시즌 결과보고서 확정 완료",

```

**중요 변경:** A-02는 이제 E-01~E-04에 개별적으로 요청하지 않고 DM-04 1곳에만 요청한다(`a02_top_level_relay_agent_prd.md` 갱신 반영).

### FN-08 연간 누계 보고 (연말 요청 시)

사서 요청 또는 12월 말 자동 트리거 시 연간 4개 시즌 실적을 취합해 연간 결과 요약을 생성한다(E-05 PRD FN-06과 동일 구성: 시즌별 운영 현황, 연간 최고/개선 필요 프로그램, 연간 예산 집행 요약, 차기 연도 기획 제언).

## 4. 데이터 흐름

```
[상위 지시 발생 시]
chief-coordinator → DM-04: 정책/기획 지시
DM-04 → 대상 리프: 지시 분배 (FN-01)

[월말 또는 시즌 기획 시점]
chief-coordinator → DM-04: 계획서 조회 요청 (FN-02)
DM-04 → E-01: 시즌 기획 진행 상태 조회
DM-04 → chief-coordinator: 계획 응답 (or unavailable)

[시즌 종료]
E-04 → DM-04: 시즌 운영 실적 데이터 (FN-03)
DM-04 → A-03: 시즌 예산 집행 현황 조회 (FN-04)
DM-04 → A-01: 결과보고서 hwpx 초안 생성 요청 (FN-05)
DM-04 → 사서: 초안 전달 → 사서 검토·결재
DM-04 → E-01: 확정 후 수강 실적 피드백 (FN-06)

[월간·연간 통계 수집 시]
A-02 → DM-04: 데이터 수집 요청
DM-04 → A-02: 표준 실적 데이터 응답 (FN-07)

[연말]
자동 트리거 또는 사서 요청 → DM-04: 연간 누계 보고 생성 (FN-08)
```

## 5. Human-in-the-loop 정책

| 단계 | 사서 개입 여부 | 내용 |
|------|--------------|------|
| 상위 지시 분배(FN-01) | 불필요(모호할 때만 확인 질문) | 자동 분배, 결과만 상위 보고 |
| 계획서 취합·전달(FN-02) | 불필요 | E-01이 이미 보유한 기획 정보를 편집만 함 |
| E-04 데이터 수신·검증(FN-03) | 불필요 | 자동 처리, 검증 실패 시만 사서 알림 |
| 예산 조회(FN-04) | 불필요 | 자동 처리 |
| 결과보고서 초안 생성(FN-05) | 불필요 | 자동 생성 후 사서에게 전달 |
| 결과보고서 검토·결재 | **필수** | 사서 확인·수정·결재 후 제출 |
| E-01 피드백(FN-06) | 불필요 | 보고서 확정 후 자동 전달 |
| A-02 응답(FN-07) | 불필요 | 요청 즉시 자동 응답 |
| 연간 누계 보고(FN-08) | 불필요 | 자동 생성 또는 사서 요청 즉시 응답 |

## 7. 예외 처리

| 상황 | 처리 방식 |
|------|----------|
| E-04 데이터 필수 항목 누락 | 누락 항목 목록화 후 사서에게 E-04 재확인 요청 |
| A-03 예산 데이터 조회 실패 | 예산 항목 공란 처리 후 사서에게 수동 입력 요청 |
| 수료율 0% 프로그램 | 개선사항에 자동 반영 + 사서에게 원인 확인 요청 |
| 전체 시즌 폐강 | 해당 시즌 보고서 생략, 폐강 사유 기록만 저장 |
| 상위 지시 대상 리프가 불명확 | 임의 배분하지 않고 chief-coordinator에 명확화 질문 |
| 연간 누계 시 일부 시즌 데이터 누락 | 누락 시즌 표시 후 가용 데이터 기반으로 생성 |

---

## 8. 비기능 요구사항

- 결과보고서는 시즌 종료 후 5영업일 이내 초안 생성을 목표로 한다.
- 자동 생성 기준값(수료율 등)은 Config에서 조정 가능하다.
- E-01 피드백 데이터 형식은 E-01 PRD의 `course_history` 테이블 구조와 완전히 일치해야 한다.
- SQLite 데이터는 연도 단위로 보존하며 삭제하지 않는다.
- 응답 언어: 한국어
